# 配置与流量分库，汇总和记录同事务

请求记录、调试原文是高频写入，Channel 配置是极低频写入。SQLite 只有一个写者，一个批量写记录的事务会把配置写操作一起堵住。所以分成两个数据库文件。

汇总统计原先放在配置库，这是错的：WAL 下跨文件事务只保证单文件原子，汇总和记录各自刷盘，崩溃后两边对不上。参考实现（ccLoad）演示了更直接的版本——它的异步写队列满了会丢批次，连已计费的用量统计都会丢，而它每行日志上都存了分钟桶，只是从来没聚合成表。

因此：`ntm.db` 只存配置；`ntm-traffic.db` 存 Request 与 Attempt 记录，以及按小时的汇总表，汇总和记录在同一批、同一个事务里写入。

后来调试原文又从流量库里分了出去，单独放 `ntm-debug.db`（Q153）。原因是它一份能有 1 MB，而且 24 小时就删一轮：这种「大块写进来、很快删掉」的表会让文件反复涨缩，得定期 VACUUM 才收得回空间，而 VACUUM 期间整个库写不进去。计费凭据不该陪着它一起停。

## Consequences

- 三个库之间都不能 join。记录行冗余存渠道名、模型名等显示所需字段，而不是只存外键。
- 崩溃最多丢最后一批（约一秒），且汇总与记录一起丢，不会互相对不上。
- 记录队列不允许丢，它携带 Cost；只有调试原文队列在压力下可丢。
- 汇总表不随保留期删除：记录保留七天，汇总永久。
- 调试库开了 `auto_vacuum = INCREMENTAL`，删完原文顺手还页，不需要停库整理。
- 库名不叫 logs。它是计费凭据，叫 logs 迟早有人把它当垃圾清掉。
- ApiKey 与 Channel 的费用上限运行时用内存计数（ADR-0003），启动时从汇总表加载累计值。
