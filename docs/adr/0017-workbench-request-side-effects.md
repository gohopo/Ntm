# 工作台的请求照常记账，但不改变选路状态

Admin 在 Workbench 里发的测试请求会真的打到上游、真的花钱，但它们和客户端请求不一样：常常故意带上游不支持的参数、故意用停用的渠道或密钥、在可用时段外或者触发上限之后试一下。问题是这些请求要不要记录、算不算钱、受不受限制，以及会不会影响 Cooldown 和 Health。

参考的几家各有做法：ccLoad 记日志、算费用但默认不进统计，成功清冷却、失败进冷却；new-api 手动测试不会让渠道被自动停用；AxonHub 的请求带来源标记。Ntm 的取舍是：钱照算，选路状态不动。

- **记录和费用**：照常记一条 Request，来源标成工作台，不属于任何 ApiKey。费用计入 Channel 的每日费用，也进 Aggregate（按 ApiKey 分组时那一行叫「工作台」）。钱是真花出去的，账上不能少。
- **失败不写 Cooldown，也不写 Health**：测试失败往往是测试本身造成的，不能因为一次测试把渠道踢出选路。
- **固定到渠道时成功清 Cooldown**：只清这次成功证明可用的那几层，即这份密钥值、密钥值加模型、渠道加模型、整个渠道。这是「充值或换了密钥之后点一下就恢复」的用法。
- **固定到渠道时不受 Restriction 约束**：可用时段、每日上限、RPM、并发、模型白名单都不拦，冷却中的密钥也照样发；但用量照常计数，之后客户端请求的限制会看到这些用量。停用的渠道和密钥也能测。
- **按下发模型测时照常遵守 Restriction**，冷却中的候选按不可用处理，也不占用冷却到期后的那一个探测名额，因为要看的是客户端会遇到什么。成功也不清 Cooldown：探测名额没被它占用，放开的时机仍交给客户端请求。
- **一律录 DebugCapture**，不看三处开关。内容是 Admin 自己写的，不涉及别人的数据。

## Consequences

- 总览上的成功率会被故意试错的测试拉低。没有为此把工作台请求排除出 Aggregate，因为那需要给汇总加一个维度，而钱必须算进去。请求日志可以按来源筛选。
- Health 只由客户端请求算出，测试成功也不会让 Health 回升；需要的是清 Cooldown，而这只在固定到渠道时发生。
- 固定到渠道的测试绕过每日上限，Admin 可以因此让渠道当天的花费超过上限。这是有意的：上限是给选路用的，不是给 Admin 用的。
- 工作台的端点在 `/api/workbench/…` 下，用管理员登录态鉴权。上游的认证失败在这里是 502，错误详情在请求记录里，不会以 401 返回，免得页面把它当成登录失效。
