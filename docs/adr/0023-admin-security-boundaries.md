# 管理接口使用来源检查和 JSON 边界，登录接受短时全局限流

管理接口与静态管理页面同源，靠单管理员 cookie 认证；工作台发送和无请求体的 POST 也能产生费用或改动状态。仅凭 SameSite=Strict 不足以覆盖同站子域等边界，因此所有 `/api` 非 GET、HEAD、OPTIONS 请求统一检查 Fetch Metadata：只接受 `Sec-Fetch-Site: same-origin` 或 `none`；缺少它时用 Origin 与外部 Host 核对来源，并要求带请求体的请求使用 `application/json`（Q351）。保留 HttpOnly、SameSite=Strict、HTTPS 下的 Secure cookie，不允许跨源管理页面。

## 为什么不加 antiforgery 令牌

ASP.NET Core Minimal API 的自动 antiforgery 支持主要覆盖表单绑定，不会自动替这些 JSON 端点完成令牌校验。可以显式实现“先取令牌、每次发送”的方案，但会增加前端和脚本的状态协议。这里选择来源检查加 JSON Content-Type 作为统一边界，避免漏掉工作台和无请求体操作；同站其他子域也拒绝，不把它们当可信来源。

缺少 Fetch Metadata 和 Origin 的请求仍允许进入认证，以兼容 curl 和脚本。这是兼容性取舍，不代表缺头就可信，也不是认证绕过：仍要有有效 cookie。缺头的浏览器请求还依赖 SameSite=Strict 等限制；代理不得删除这些来源头，必须保留外部 Host 和端口，并配置可信代理以恢复外部协议；省略端口时按有效协议归一化为 HTTP 80 或 HTTPS 443，不为错误的代理配置放宽来源检查。若以后支持跨源管理前端、放宽 SameSite 或需要覆盖更老的浏览器，这个决定必须重新评估，而不能只加宽放行名单。防护不应用到使用 API 密钥的 `/v1` 转发接口。

## 为什么接受短时全局拒绝登录

只有一个管理员，永久锁号或按账号长时间锁定会给攻击者一个简单的拒绝服务开关；只按 IP 限制又挡不住多地址猜测。选择每个来源一分钟最多失败 5 次（IPv6 按 /64），再加全局一分钟最多失败 30 次，登录成功不累计；改密码中的旧密码验证共享限制（Q353）。超限返回 429 和等待时间，窗口结束自动恢复，不要求人工解锁。计数只在内存里，符合 ADR-0003。

代价是分布式攻击仍可在每个新窗口再次耗尽额度，让管理员持续无法新登录。限流减少密码猜测，不提供入口可用性保证；公网部署仍应在反代上限制管理入口的来源。已有管理会话和 API 密钥转发不因登录限流失效。

## 相关安全边界

- 不再自动生成并把默认 API 密钥写进日志（Q350）；页面上新建的 API 密钥只显示一次。已有密钥不自动撤销。
- 为了无额外文件复制步骤的首次部署体验，仍允许生成管理员密码并输出；但生成或命令行重置的密码必须先更换，才能使用其他管理功能（Q349）。这缩短了日志中密码的有效期，不会清除已有日志。
- 操作记录只保存动作、对象和变化字段名，不保存字段值；它是排错记录，不是防篡改的合规账本。工作台调用继续放在请求记录里，避免两个“日志”混淆（Q358）。
