# 同协议透传：定点改写字节，旁路嗅探用量

入站 API 格式与上游 API 格式相同时，不把请求解析成 IR 再序列化出去，避免「转一圈再转回来」丢字段。但也做不到完全不碰字节：选路要读 `model`，渠道改写规则要落到请求体上，流式 OpenAI Chat 还得注入 `stream_options.include_usage` 才拿得到 Usage。

因此透传的定义是：请求只解析一次拿到选路字段，然后对客户端的原始字节做定点改写（模型名替换、渠道级改写规则、注入 `include_usage`），其余原样发出；响应原样转发，挂一个只读旁路嗅探器抽取 Usage 与停止原因。客户端自己没要用量时，网关为计量注入而多出来的那个 usage 事件在转发前吞掉。透传是为了保真，不是为了省一次解析。

## Consequences

- 响应里的 `model` 是 UpstreamModel 的名字，不改写回客户端请求的 PublishedModel 名：OpenAI Chat 流式每个 chunk 都带 `model`，改写它等于放弃字节级转发。代价是客户端能看到上游模型名。
- 每种 API 格式各维护一套嗅探规则与改写位置。
- 渠道带 RewriteRule 时是例外（Q147）：规则能改任意嵌套字段，逐个写成定点改写不现实，所以这一个渠道的请求体会解析成 JSON 树、改完重新序列化。JSON 树往返不丢未知字段，丢的是缩进、空白与转义写法，所以发往上游的字节不再和客户端发来的完全一致。没有规则的渠道不受影响，仍走定点改写。规则先跑，网关自己的改写（模型名、`include_usage`）后跑，规则写错也改不掉选路和计费依赖的字段。

## Considered Options

- 放弃同协议的精确计量，按长度估算 Usage：费用追踪会系统性偏差，不可接受。
- 永远解析成 IR 再序列化：丢失 API 格式专有字段，且给透传路径加上不必要的转换开销。
