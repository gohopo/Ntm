# Responses 的按 id 端点：落点存进库，只回产出它的渠道密钥

OpenAI Responses 有一批按 id 访问上游状态的端点：取回、删除、取消一次响应（`/v1/responses/{id}`、`/cancel`），列它的输入项（`/input_items`），以及上游对话（`/v1/conversations` 和它的条目）。`background` 模式也靠它们：先拿到一个排队中的 id，之后按 id 取回结果。这些状态只存在产出它的那个账号里（ADR-0016），网关不认识 id 就不知道该发给谁。

**网关把「id → 落点」存进流量库的 `response_landings` 表。** 落点是 Channel、ChannelKey 的指纹、上游模型、产出它的 ApiKey、下发模型和那次请求的 id。内存里的表留作缓存，没命中再查库。这样重启后 `previous_response_id` 链、background 取回和对话都还能用，修掉了 ADR-0016 里「重启就断」的代价。保留 30 天（按最后一次使用，`Ntm__Traffic__LandingRetentionDays`，和请求记录的保留期分开），由已有的清理任务删；表有条数上限，满了先删最久没用的。没有改写 id（LiteLLM 那样把落点编进 id）：id 是上游给的，原样给客户端，客户端或别的工具拿着它直接去上游也能用。

**按 id 的请求只发往落点那把 ChannelKey，不选路、不重试、不换候选。** 别的账号只会回「找不到」。落点的渠道或密钥停用了、删了、换了值或解不开，就回 502 说明原因；上游回 401/403 也换成 502，因为那是渠道密钥的问题，客户端拿到 401 会以为自己的 API 密钥错了。这些请求不看冷却、费用上限、时段、RPM 和并发：它们大多是取回已经付过钱的结果，挡掉只会让 background 的结果取不回来。仍然检查 ApiKey 是否有效、下发模型和渠道是否允许它用。

**落点绑定 ApiKey。** 请求的 ApiKey 必须是产出它的那把（工作台算 0），否则当作不认识，回 404。不然拿到别人 id 的人能读、能删别人的响应。网关不认识的 id 一律 404，绝不盲转到某个渠道。

**取回、列输入项、`input_tokens` 不写请求记录；删除和取消只写一行服务日志。** 它们不产生用量，写进请求日志会把统计和费用页面冲淡。`/v1/responses/compact` 照常选路、写记录、按返回的用量记账，它产出的 `cmp_` 不记落点（compact 是无状态的）。

**background 的用量取回时回填。** 排队时上游还没有用量，原请求记下的是 0。按 id 取回、看到终态且带用量时，网关把用量和费用补进原请求的记录、汇总和费用账本，每个落点只补一次，请求状态不改。客户端一直不来取时网关自己去拉（Q305）：落点建好 30 秒后拉第一次，之后每分钟一次，满 10 分钟后每 10 分钟一次，满 1 小时后每 30 分钟一次（Q317，一个响应最多拉约 60 次），同时最多 4 个；规则和按 id 的端点一样，只发产出它的那把 ChannelKey，不看限制、不写请求记录。到了终态照上面回填；上游回 404 或满 24 小时还没终态就放弃，用量留空并写一行日志。等用量的标记存在落点表里，重启后接着拉，客户端和网关同时取到也只补一次。

**渠道可以声明「密钥属于同一个账号」（Q306）。** 默认关，行为同上。打开后落点只固定 Channel：`previous_response_id` 和 `conversation` 先用产出它的那把 ChannelKey，它停用、删了、在冷却或被限制时换这个渠道的别的密钥，照常按密钥级失败往下换；按 id 的端点仍只发一次，产出它的密钥还在就用它，否则用优先级最高的那把。这是给同一账号开了多把密钥的渠道用的；密钥分属不同账号时打开，换了密钥上游只会说找不到。

**上游对话按同样的规则固定。** `POST /v1/conversations` 在这个 ApiKey 能用的 Responses 渠道里，按优先级、渠道 id 挑第一个有不在冷却的密钥的，建在那里并记下落点；之后带 `conversation` 的请求和对话的其他端点都回到那里。`conversation` 和 `previous_response_id` 只能用一个；`item_reference` 要和其中一个一起用才放行，因为它引用的条目也只存在那个账号里。

## Consequences

- 落点表让流量库多了一类会持续增长的数据；条数上限和保留期管住它，代价是很久没用的 id 过期后只能重发完整上下文。
- 同一个账号下的多把 ChannelKey 本来互相读得到对方的响应；网关默认仍只认产出它的那一把，要换密钥得在渠道上声明「密钥属于同一个账号」。这个开关网关验证不了，填错了只会换来上游的「找不到」。
- 主动拉用量会多一些发往上游的 GET；每个 background 响应最多拉到 24 小时，大约 150 次。
- 删除对话后它的落点留到过期，再来的请求由上游回答「不存在」；删除响应成功则落点一起删。
- 网关不在本地重建上下文、不模拟 compact，也不支持 Responses 的 WebSocket 模式。
